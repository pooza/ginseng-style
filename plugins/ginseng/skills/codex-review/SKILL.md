# Codex のレビューを処理する

PR には Codex（`chatgpt-codex-connector[bot]`）のレビューが遅れて届く。⚠ **以下は Codex 名で書いてあるが、自動レビュー全般に効く**（実装を替えても中身は変わらない）。

⚠⚠ **正本はこのファイル。** [docs/workflow.md](https://github.com/pooza/ginseng-style/blob/main/docs/workflow.md) の「Codex のレビュー」はここへのポインタ。

## 手順

1. **走査する** — 4 経路すべて（下記「指摘なしを、レビューが動いていないと読まない」）
2. **採否を決める** — 下の表。⚠ **判断の前に測ることが 3 つある**
3. **返信と 👍 / 👎 の両方を付ける** — 片方だけは未処理と同じ
4. **締める直前にもう一度走査する** — 走査したあとに着いたものがそのまま落ちる

## 採否を決める

⚠⚠ **妥当かどうかは毎回測るしかない。規約にできるのは「判断の前に何を測るか」だけ。** 2026-08-27 の #65 の配布では 4 件のうち **2 件が成立しなかった**（うち 1 件は P1）。

| 判定 | やること | 再レビュー |
| --- | --- | --- |
| **P1・妥当** | 修正する | ⚠ **`@codex review` を投げて再レビューする** |
| **P2・妥当** | 修正する | 不要 |
| **妥当でない** | 修正しない | 不要。⚠⚠ **👎 に反証の実測を添える** |
| **妥当だが当てられない** | Issue に切る | 不要 |
| 🔴 **妥当だが、この PR では直さない**（⚠⚠ **P2 / P3 だけ**） | **Issue に切る**。⚠⚠ **返信に番号を書く** | 不要 |

⚠ **P0 は P1 と同じ扱い、P3 は P2 と同じ扱い。** ただし 2026-08-27 に `ginseng-*` 8 リポジトリの Codex コメントを全部数えたら、**73 件はすべて P1（17 件）か P2（56 件）**で、P0 / P3 は 1 件も出ていない。

⚠ **「妥当だが当てられない」は逃げ口上ではない。** 横断の不変条件を壊す指摘がここに入る。⚠⚠ **`ginseng-*` の横断的な判断は `ginseng-style` に Issue を立てる**（[docs/CLAUDE.md](https://github.com/pooza/ginseng-style/blob/main/docs/CLAUDE.md)）。

⚠⚠ **下 2 行は「Issue に切る」で同じだが、意味が違う。** 前者は**やらないと決めた**（横断の不変条件を壊す・当てる先が無い）、後者は**やる。順番が後**（`size:L` になる／`breaking` で予告が要る／別のマイルストーンに属する）。⚠ 混ぜると、やると決めたものが「当てられない」に紛れて消える。

🔴 **深刻度が勝つ。P0 / P1 を「妥当だが当てられない」にも「この PR では直さない」にも落とさない**（pooza/ginseng-style#85）。⚠⚠ **表の行が重なったら、深刻度の高い行を採る**（`breaking` / `size:L` / 横断の不変条件を壊す、のいずれとも）。⚠ そのうえで、**出どころ**で切り分ける。

⚠⚠ **P0 は出どころで切り分けない。** 出どころに関わらず**修正するか、マージしない**。⚠ 下の表は **P1 だけ**に効く（上の「P0 は P1 と同じ扱い」の例外。リリースを普遍的に止める重大障害を「元からある」で出荷できてしまうため）。

| P1 | やること |
| --- | --- |
| **この PR で入った／この PR の変更で踏むようになった** | ⚠⚠ **直すか、PR をマージしない。** 後回しにしない |
| **この PR と無関係に元からある** | Issue に切ってよい。⚠ **次の版のマイルストーンに載せる**（先送りの受け皿を必ず作る） |
| 🔴 **どちらとも言い切れない**（触った行に元からあった、など） | ⚠⚠ **直す側へ倒す。** 出どころの切り分けに悩む時間のほうが高い |

⚠⚠ **順番を上げる手段にラベルを使わない。** `security` は「セキュリティに関わるもの」の印であって重要度の印ではない（[docs/workflow.md](https://github.com/pooza/ginseng-style/blob/main/docs/workflow.md) の「共通のラベル集合」）。⚠ **P1 には可用性・データ破損・性能も入る**ので、一律で付けると **`security` での棚卸しが濁り、本物の脆弱性の集合が壊れる**。順番はマイルストーンで表す。

⚠ **`breaking` で予告が要るから直せない、は「マージしてよい」理由にならない。** 予告の Issue を立てて、**その修正が入るまで元の PR を止める**。

⚠⚠ **「当てられない」も同じ。** 当てる先がこのリポジトリに無い P1（横断の不変条件を壊す等）は、**当てられる場所に Issue を立て**（`ginseng-*` の横断なら `ginseng-style`）、**そこが塞がるまで元の PR を止める**。🔴 **「当てられない」はマージしてよい理由にならない。**

🔴 **「この PR では直さない」を無印で残さない。** 走査は**返信と 👍 / 👎 の有無しか見ない**ので、Issue を立てずに返信して 👍 を付けると、**直っていないものが完了として消える**。「取り残さない」（下記）が守ろうとしているものが、ちょうどここで抜ける。

### ⚠ 判断の前に測ること

**① 前提を測る。** ⚠⚠ **Codex は 1 リポジトリしか見ていない。対処が別リポジトリにあると「無い」と読む。**

> 実例（2026-08-27）: 「`workflow_dispatch` は任意のブランチで回せるので、未マージのコミットに公開タグが付く」という **P1**。⚠ **そのガードは呼び出し側ではなく [release-tag](https://github.com/pooza/ginseng-style/blob/main/.github/actions/release-tag/action.yml) の中に既にあった。** 前提を確かめずに直していれば、8 リポジトリの caller に同じ判定を写して、直すときに 8 箇所を追うことになっていた。

**② 前例を引かれたら前例を見る。** ⚠ **食い違うことがある。**

> 実例（2026-08-27）: 「`required_ruby_version` の引き上げは major にすべき。このリポジトリは前に major で出している」という P2。裏は取れた（`ginseng-youtube` は `2.6`→`3.3` を `v2.0.0` で出していた）が、⚠⚠ **`ginseng-postgres` は `2.6`→`3.0` を `v1.3.12`（patch）で出していた。** 前例では決まらないので、**実害の記録**で決めた — patch で `>=3.4` に上げて利用側の CI を落とした [pooza/ginseng-style#63](https://github.com/pooza/ginseng-style/issues/63) がある。**結論は「指摘どおり major」だが、根拠は指摘の根拠と違う。**

**③ 横断の不変条件を壊さないか。** ⚠⚠ **1 リポジトリで妥当な指摘が、8 リポジトリでは当てられないことがある。**

> 実例（2026-08-27）: 「動くタグでなく SHA で固定しろ」という P2。技術的には正しいが、⚠ **1 本だけ SHA にすると [gem-watch](https://github.com/pooza/ginseng-style/blob/main/.github/workflows/gem-watch.yml) の `pins` が `vX.Y.Z` 以外を error にしているので赤くなる。** さらに参照経路は 2 つあり（`ruby-check` と `release-tag`）、片方だけ固めても脅威モデルが変わらない。→ [pooza/ginseng-style#75](https://github.com/pooza/ginseng-style/issues/75)

### 🔴 👎 は「直さない」の逃げ道になる

⚠⚠ **反証の実測を添えられないなら、それは 👎 ではない。** 規律を書いておかないと、**面倒な指摘ほど「成立しない」で閉じられる**ようになり、運用が静かに劣化する。

- 却下の返信には、**どこを見て・何が違ったか**を書く（ファイルと行、実測した値）
- ⚠ 「たぶん大丈夫」「設計上そうなっている」は反証ではない
- ⚠⚠ **P1 を却下するときほど厚く書く。** 次のセッションが同じ検証をやり直さずに済む形にする

## 取り残さない

**返信と 👍 / 👎 の両方を付けて完了**とする。⚠ **両方が揃っていないもの ＝ 未処理**、という判定に使えるようにするため。

- ⚠⚠ **却下する指摘にも 👎 を付ける。** 何も付けずに残すと、**次のセッションが同じ検証をやり直す**

### 🔴 「指摘なし」を「レビューが動いていない」と読まない

⚠⚠ **Codex は結果の出し方を 3 通り持っている。**

| 結果 | どこに出るか |
| --- | --- |
| 指摘あり | **review**（`pulls/N/comments` に行紐づきで届く） |
| **指摘なし** | **issue コメント**1 本（`Didn't find any major issues.`）。⚠ **review は作られない** |
| 🔴 **指摘なし** | **PR 本体への 👍**（`issues/N/reactions` の bot の `+1`）。⚠⚠ **review でもコメントでもない** |
| 🔴🔴 **まだ結果ではない** | **PR 本体への 👀**（同じ `issues/N/reactions` の `eyes`）。⚠⚠ **「読み始めた」の合図で、成果物ではない** |

⚠ Codex 自身の説明文がそう言っている — *"If Codex has suggestions, it will comment; otherwise it will react with 👍."*

🔴🔴 **ただし 👍 は「この PR に指摘が無かった」ではない。「ある巡が指摘なしで終わった」だけ。** ⚠⚠ **指摘が 6 件出た PR にも 👍 が付く。**

> 実測（`pooza/ginseng-core#607`）: codex のインライン **6 件**（10:53 / 11:02 / 11:12 / 21:25 / 21:37 / 21:42）に対し、👍 の `created_at` は **21:56** — **最後の巡が綺麗だった**ところに付いている。⚠ リアクションは 1 ユーザー 1 個しか持てないので**巡ごとには増えない**。

- ⚠ **「👍 が付いている ＝ 見なくてよい」ではない。** インラインを別に見る
- ⚠⚠ **だが `created_at` は巡を指す**（上の 21:56 > 21:42）。待ち方に使えるのはこちらだけ

⚠ **`.reviews[]` だけを見ると、指摘が無かった PR が「レビュー 0 件」に見える。**

> 実例（2026-08-27）: `.reviews[]` だけで 8 リポジトリを走査し、**`ginseng-piefed` は Codex が繋がっていない**と結論して Issue まで立てた。⚠⚠ **実際は繋がっていて、過去の PR が全部「指摘なし」だっただけ**。さらにその PR 群は**作成からマージまで 1〜23 分**で、レビューが返る前に閉じていた。

- **走査は 4 経路。** `pulls/N/reviews`（本文）・`pulls/N/comments`（インライン）・`issues/N/comments`・🔴 **`issues/N/reactions`**。⚠ 片方だけの走査は「無い」の根拠にならない
- 🔴🔴 **リアクションは `content == "+1"` で絞る。** ⚠⚠ **bot は結果より先に 👀 を付ける**ので、`.user.login` だけで絞ると**「レビューが着いた」が PR 作成の数秒後に成立する**
  > 実測（[pooza/ginseng-style#100](https://github.com/pooza/ginseng-style/pull/100)）: PR 作成 `07:42:04` → bot の `eyes` `07:42:10`。⚠ **その時点で reviews / インライン / issue コメントはすべて 0 件**だった。⚠⚠ 下記「取り残し」の走査で `reactions.total_count` を禁じているのと**同じ理由が待機ループにも効く**
  - ⚠ **`eyes` は終了条件に入れない。** 入れるなら「まだ来ていない」側の傍証として使う
- 🔴 **待機ループの終了条件も 4 経路で組む。** ⚠⚠ **「無いの測り方」を知っていても、終了条件に写さなければ意味が無い** — 1 巡目が review で来ると、待ち方までその形に引っ張られる
  > 実例（2026-08-31）: [pooza/ginseng-style#97](https://github.com/pooza/ginseng-style/pull/97) の 2 巡目を `until .reviews[] が 2 件になるまで` で待って 10 分 timeout した。⚠ **👍 だけの巡なら永久に来ない条件**で、timeout したとき**「まだ来ていない」のか「拾えない形で来ていた」のかを区別できていなかった**
- 🔴🔴 **ただし「4 経路の OR」だけでは 2 巡目以降で即座に成立する。** ⚠⚠ **前の巡の review・コメント・👍 が全部残っているので、条件は最初のポーリングで真になる** ＝ **待たずに「指摘なし」と判断する**
  - **巡を起こす前に基点を採る。** 各経路の**件数と最大 id**、👍 は **`created_at`**。⚠ 終了条件は「**基点より新しい bot の成果物が在るか**」
  - ⚠ **基点は自分の返信より前に置く。** 後ろに置いて P1 を一度取りこぼした（`pooza/ginseng-core#612`）
  - ⚠ **👍 の「在る／無い」は基点に使えない**（1 ユーザー 1 個で増えないため）。使えるのは `created_at` だけ
- ⚠ **応答が無いことを数分で判断しない。** Codex は遅れて届く
- ⚠⚠ **「繋がっていない」を報告する前に、無いことの測り方が正しいか確かめる**
- 直せるものは修正 PR、**当てられない／この PR では直さない**ものは Issue を立ててから返信する（⚠ 返信に番号を書く）。⚠⚠ **成立しない指摘にだけは Issue が要らない** — 👎 と反証の返信で完了（上記「採否を決める」）
- ⚠⚠ **窓を件数で切らない。** Codex はマージ後に届くので、PR の流量が多い時期ほど新しい PR に押し出される。実例: モロヘイヤで **P1 が 2 件、4 日放置**された（「SSRF を塞いだ」という認識のまま、実際には塞げていなかった）
- ⚠⚠ **PR を出したセッションは、締める直前にもう一度走査する。** 走査したあとに着いたコメントがそのまま落ちる。「さっき棚卸しした」は理由にならない

### ⚠⚠ 2 つの問いを混ぜない

| 問い | 走査 |
| --- | --- |
| **取り残しはないか**（未処理の指摘を探す） | リポジトリ全体の `pulls/comments`（下記）。⚠ 👍 だけの巡は**処理するものが無い**ので出なくてよい |
| 🔴 **そもそも発火しているか**（「繋がっていない」を疑うとき） | ⚠⚠ **`pulls/comments` だけでは答えられない。** 👍 しか返っていないリポジトリは「0 件」に見える（2026-08-27 の `ginseng-piefed`） |

🔴 **`issues/N/reactions` は PR 番号ごとにしか引けない**ので、下の「PR を列挙して回さない」とそのままでは両立しない。⚠⚠ **禁じているのは「件数で窓を切ること」**であって列挙そのものではない。**`--paginate` で全部並べてから絞る。**

```sh
# ⚠⚠ issue の一覧はリアクションの集計を持っているので、ここで候補を絞れる。
gh api --paginate "repos/$repo/issues?state=all&per_page=100" >| /tmp/issues-raw.json \
  || { echo '走査に失敗した。結果を信用しないこと' >&2; exit 1; }
jq -s add /tmp/issues-raw.json >| /tmp/issues.json
jq -r '.[] | select(.pull_request) | select(.reactions["+1"] > 0) | .number' /tmp/issues.json

# ⚠ 誰が付けたかは一覧に載らない。候補だけ引き直す。
# ⚠⚠ content で絞る。bot は結果より先に 👀（eyes）を付ける。
gh api "repos/$repo/issues/$n/reactions" \
  --jq '.[] | select(.user.login == "chatgpt-codex-connector[bot]" and .content == "+1") | .created_at'
```

⚠ 実測（2026-08-31・`ginseng-core`）: **PR 236 本を 2 リクエストで並べ、👍 付き 45 本に絞れた**（既知の `#619` を含む）。⚠⚠ **既知の 1 件を拾えることを先に確かめてから件数を語ること。**

**PR を列挙して回さない。** リポジトリ全体のレビューコメントを `--paginate` で取る。

```sh
repo=<owner>/<repo>
# ⚠⚠ gh を単独で走らせ、終了ステータスを見てから jq に渡す。パイプで繋ぐと
#   パイプ全体の状態が jq のものになり、ページングの途中で失敗しても
#   「出し終えた分だけ」を全履歴として走査してしまう ＝ 偽のゼロ。
# ⚠ 上書きは >| で。zsh の noclobber を有効にしていると > が既存ファイルを拒む。
gh api --paginate "repos/$repo/pulls/comments?per_page=100" >| /tmp/codex-raw.json \
  || { echo '走査に失敗した。結果を信用しないこと' >&2; exit 1; }
jq -s add /tmp/codex-raw.json >| /tmp/codex.json
jq -r '. as $all | $all[] | . as $c
  | select(.user.login == "chatgpt-codex-connector[bot]")
  # ⚠⚠ GitHub は返信をスレッドの**根**に紐づける。$c.id で引くと入れ子が永久に残る。
  | (.in_reply_to_id // .id) as $root
  | select(([$all[] | select((.in_reply_to_id // .id) == $root)
                    | select(.user.login != "chatgpt-codex-connector[bot]")
                    | select(.created_at > $c.created_at)] | length) == 0
           or ((.reactions["+1"] // 0) + (.reactions["-1"] // 0)) == 0)
  | "PR#\(.pull_request_url | split("/") | last) \(.id) \(.path)"' /tmp/codex.json
```

- ⚠⚠ **`gh pr list --limit N` で回す形にしない。** N 本より古い PR に遅れて届いたレビューへ永遠に到達しない ＝ **この節が防ごうとしている失敗そのもの**
- ⚠ **`gh api` は `--paginate` を付けないと 1 ページ目しか見ない**
- ⚠⚠ **`gh api ... | jq` と繋がない。** 失敗したページングを握り潰し、**部分的な結果を「全部見た」として扱う**
- ⚠ **zsh の `noclobber` を有効にしていると `>` が既存ファイルを拒む。** 2 回目の走査が `file exists` で落ちるので、`>|` で上書きする（⚠ 上の例も 2 か所とも `>|` にしてある。**書き換え忘れると、注意書きの直後の例がその注意どおり落ちる**）
- ⚠⚠ **`reactions.total_count` を完了判定に使わない。** 👀 や ❤️ が 1 つ付いただけで非ゼロになり、**未処理のものが走査から消える**。**返信の有無**と **👍 / 👎 の数**を別々に見る
- 🔴 **返信は「そのコメント宛」では引けない。** ⚠⚠ **GitHub はスレッドへの返信を必ず根のコメントに紐づける** — `pulls/{n}/comments/{id}/replies` に入れ子の `id` を指定して投げても、返る `in_reply_to_id` は**根**になる。`in_reply_to_id == $c.id` で引くと、**スレッドの 2 通目以降は返信も 👍 も付いているのに永久に「未処理」として出続ける**（実測: `pooza/ginseng-style#87` の `id=3876427332`）
  - **スレッド単位で「その指摘より後に来た、bot 以外の返信」を見る**（上の jq）
  - ⚠ **「後から来た」で見ること。** 根への返信を無条件に数えると、**新しい指摘が古い返信で消える**
  - ⚠⚠ **消えない未処理を出し続ける走査は、走査ごと信用されなくなる。** ここが濁ると、この節が防ごうとしている取り残しがノイズに紛れる
