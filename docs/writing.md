# 表記規約

ドキュメント・Issue・コミットメッセージ・コードコメントに共通の表記。

## 言語

日本語で書く。

## 用語

- **サーバー** — Fediverse のサーバーを「インスタンス」と呼ばない。⚠ **理由: 一般的な表記規約ではなく、上流の公式表記に従っているだけ。** Mastodon が「インスタンス」という用語を廃止して「サーバー」に改め、Misskey も後追いで同じ変更をした。⚠⚠ **適用範囲はそこまで。** 一般語としての instance（クラスのインスタンス、実行中のプロセスの実体）はそのまま使う
- **WebUI** — サーバーが提供する Web の画面は「UI」と呼ばない。⚠ **理由: クライアントアプリの UI と区別する必要があるから。** Mastodon / Misskey について「UI」とだけ書くと、**サーバー側の WebUI なのか、それを叩くクライアントアプリの UI なのかが判別できない**。⚠ **常に言い換えよという規約ではない** — どちらを指すか文脈で明らかなら、そのままでよい
- **IP アドレス** — 「IP」単独で使わない。⚠ **理由: 「IP」はプロトコルの名前であって、アドレスを指す語ではない。** 略した結果べつの概念を指してしまう省略は避ける（JavaScript を Java と呼んではいけないのと同じ）。⚠ 文書では例外なく守る。コードコメントは目を瞑るが、揃えられるなら揃える
- **役割名で呼ぶ** — ボットや常駐プロセスは英識別子（`info_bot` 等）ではなく日本語の役割名（「お知らせボット」等）で書く

## パスとキーの書き方

- **設定ファイルのパス**: ディレクトリを含めて表記する（`local.yaml` ではなく `config/local.yaml`）
- **設定キーの参照**: ginseng のスラッシュ記法で表記する（`sidekiq.auth.user` ではなく `/sidekiq/auth/user`）
- **ファイル参照**: サンプルやテンプレートへの参照はマークダウンリンクにする

## クロスリポジトリの Issue 参照

`owner/repo#number` の形で書く（`pooza/chubo2#141`）。同一リポジトリ内は `#141`。

## インデント

⚠ **常に論理的な 2 スペース。** 見栄えのための位置揃えはノイズとして扱う。Markdown の表・YAML・コードすべてに適用する。

## ⚠ マーカーの使い方

読み手が読み飛ばすと事故になる箇所に付ける。**多用すると効かなくなる**ので、段落の格付けとして使う。

| マーカー | 意味 |
| --- | --- |
| ⚠ | 見落とすと間違える前提・地雷 |
| ⚠⚠ | 見落とすと事故になる。判断の分岐点 |
| 🔴 | 実際に壊れている・壊した箇所 |
| ✅ | 正しい形・着地済み |

## 記録するときは「指示」ではなく「理由」まで書く

⚠ 文言だけを残すと、誤りではなくても後から判断に使えない。「なぜそうなのか」「どういう文脈で決まったか」まで書く。

（実例: 「週明けに着手」と記録したが、実体は「日曜朝の実況が終わるのを待つ」だった。文言だけでは月曜起点と読める）
