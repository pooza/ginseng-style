# セッション開始時の同期

`ginseng-*` に届いているものを横断で集め、次に何をすべきかを順位を付けて報告する。

⚠ **本体は読むだけ。** 外へ書く操作（ラベル・コメント・起票）は報告のあとにする（[docs/skills.md](../../../docs/skills.md) の「同期」の例外）。

⚠ **各アプリの `/sync` とは別物。** あちらはそのプロジェクトの状態を見る。`ginseng-*` の Issue の優先度付けは、管理拠点であるここの役割。

## 1. 現在地を読む

- `git fetch origin` のあと `git status -sb`。⚠ 手元の状態を信用しない
- メモリの `project_kickoff.md` の最新の節で、前回の日付・判断待ち・未マージを確認する

## 2. 集める

リポジトリのルートから、前回の日付を渡して実行する。

```sh
GINSENG_SYNC_EXTRA_REPOS='<他 org のリポジトリ>' .claude/skills/sync/scripts/inbox.sh <前回の日付>
```

- 他 org のリポジトリ名はメモリの `project_ginseng-consumers.md` にある
- ⚠⚠ **`🔴 取得失敗` の行があるか、終了コードが 1 なら、その範囲は「0 件」ではなく「未確認」として報告する**
- gem-watch は週次（月曜）なので、最新実行の日付を報告に添える

## 3. 依頼を見分ける

⚠⚠ **`request` ラベルだけでは足りない。** 2026-11-01 の実測では、依頼 3 件のうちラベルが付いていたのは 1 件だけだった（残りは既存 Issue へのコメントと、ラベルの無い Issue）。Issue の作成者も全部 `pooza` なので区別に使えない。

次のどれかに当たれば、中身を読んで判断する。

- `request` ラベルがある
- 前回以降のコメントで、利用側が実測や依頼を報告している（コメントが既存の Issue に付くと、Issue の一覧では更新日しか変わらない）
- 本文の「依頼の候補」に出ている
- アプリ側からの参照に、自分の告知ではないものがある

⚠ 通知 API は依頼の検出に使わない。大半が自分の PR で埋まる。

## 4. 順位を付ける

依頼 → 緊急 → 効果の順。

| 段 | 当てはまるもの |
| --- | --- |
| 依頼 | 利用側からの依頼。相手の緊急性に配慮する（[workflow.md](../../../docs/workflow.md) の「着手順」） |
| 緊急 | 進行中の実害・security。実例があるか、既定の経路に効くかで重みを付ける |
| 効果 | 束ねると片付くもの、繰り返し起きている問題の根を断つもの |

⚠⚠ **運用の Issue は高めに評価する。ただし最優先にはしない**（オーナー判断・2026-11-01）。放っておくと実装の不具合が上に来続けて運用が着手されず、逆に上げすぎると実作業が止まる。

- **上げるのは上位 3 件につき 1 件まで。** 残りの運用の Issue は通常どおり評価する
- **運用の判定:** `ginseng-style` の Issue は原則すべて運用とみなす。このリポジトリは横断の話題だけを受ける場所なので。ただし、記録（`#119` の台帳）と外部を待っているものは除く
- 同じ効果なら古いものから

順位の低いものが着手されないのは許容する（オーナー判断）。

⚠ **同じ話題は束ねる。** 同じモジュールの Issue を別々に並べない。

## 5. 報告する

1. **判断待ちを最初に書く。** 何を決めれば進むかを、1 件ごとに書く
2. 順位の表（順・対象・種類・理由）。上位 5 件ほどでよく、低いものを全部は並べない
3. 今は動かさないものと、その理由を短く
4. 確認の範囲（未確認の範囲、gem-watch の日付、Issue の本文まで読んでいないもの）

⚠ **順位の理由にした事実は、Issue の本文かコメントで確かめてから書く。** タイトルだけで判断したものは、そう書く。

## 6. 報告のあと

ここから外へ書く。

- ラベルの無かった依頼に `request` を付ける（[workflow.md](../../../docs/workflow.md) の「着手順」）
- 判断や着手の結果をメモリの `project_kickoff.md` に残す
